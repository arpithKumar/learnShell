`test` evaluates a condition — does this file exist, are these two strings equal, is this number greater than that one — and reports the result purely through its exit status: success if the condition is true, failure if it isn't. It doesn't print anything; its entire job is to be checked by something else, almost always an `if` statement.

The square-bracket syntax most people actually type, `[ -f file.txt ]`, is `test` wearing a more readable disguise — `[` is genuinely a command (an alias for `test`), and the trailing `]` is a required argument that closes it, not special shell syntax. Both forms behave identically; the brackets just read more like a familiar conditional from other languages.

Because `test` is fundamentally about strings and arguments, unquoted variables are its most common failure mode — if a variable is empty or contains spaces, `test -z $name` can silently fall apart into the wrong number of arguments. Quoting consistently (`test -z "$name"`) avoids the entire category of bug.
